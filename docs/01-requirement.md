## 一、需求概述（五要素）

| 要素 | 结论 |
|------|------|
| **业务目标** | 用一款自营 App 承接"小额、短期、高频"的现金周转需求，把获客—授信—放款—还款—催收全链路做成可运营、可量化、可复借的闭环，首年核心指标为**放款件均 3,000~8,000 元、首借通过率 25%~35%、首期逾期率（DPD1）< 4%**。 |
| **目标用户** | C 端：22~45 岁、月收入 5,000~15,000 元、有稳定工作但现金流错配的城市工薪/小微经营者。B 端：运营、信审、风控、催收、财务五类岗位。 |
| **核心场景** | 发薪日前 7~15 天的临时性资金缺口（房租、医疗、进货、还款周转），用户在手机上 3 分钟内完成申请并拿到钱；到期前 3 天被提醒还款，一键还清后额度恢复、可再次支用。 |
| **关键流程** | 注册 → 实名三要素 → 活体 → 联系人授权 → 授信申请 → 风控决策 → 额度定价 → 借款下单 → 放款 → 账单 → 还款/提前结清 → （逾期）→ 催收 → 结清复借。 |
| **约束条件** | 客户端 RN + Expo（TS），服务端 Node + Express + TS + SQLite，运营后台 Vite + React（/admin）；资金、征信、人脸、短信全部走**模拟适配层**（签名对齐真实厂商，可插拔）；本阶段交付目标为**功能完备的可运行系统**，非界面演示，但**不具备真实展业资质**，定位为产品验证/POC 与合作洽谈 Demo。 |

### 1.1 一句话定位

> UCash 是一个"**3 分钟到账、费用一次说清、额度可循环**"的小额现金贷 App：不做大额长期，只做 500~20,000 元的短期周转，用透明定价和极速体验换复借率。

### 1.2 边界声明（必须先说清，避免后续预期错位）

- 本项目**不是**可立即对外放款的生产系统。真实放款需：网络小贷牌照（或与持牌资金方助贷合作）+ 征信接入 + 等保 2 级 + 应用商店金融类目资质。

## 二、用户角色与画像

### 2.1 C 端借款人（按生命周期分群，非按人群分群）

C 端不是一类人，而是**同一类人的五个阶段**。每个阶段的首页、CTA、埋点目标都不同——这是现金贷产品设计的核心，不能只做一个首页。

| 分群 | 定义 | 核心诉求 | 首页主 CTA | 关键指标 |
|------|------|----------|-----------|----------|
| **S0 游客/未注册** | 未登录 | 知道"能借多少、贵不贵" | 立即申请（走注册） | 注册转化率 |
| **S1 已注册未实名** | 有账号，无授信 | 怕麻烦、怕信息泄露 | 继续认证（显示进度条 1/4） | 实名完成率 |
| **S2 已授信未借款** | 有额度，零在贷 | 观望利率，比价 | 立即借款（显示可用额度） | 首借转化率 |
| **S3 在贷用户** | 有未结清借款 | 别忘还款、想提额 | 去还款（显示本期应还） | 按时还款率、复借率 |
| **S4 逾期用户** | 有 DPD≥1 账单 | 缓解压力、怕被催 | 立即还款（显示逾期天数与罚息） | 回款率、催回率 |
| **S5 结清用户** | 全部结清 | 下次能不能更快、更多 | 再借一笔（显示"额度已恢复"） | 复借率、提额接受率 |

**画像要点（用于文案与风控特征设计）**

- 典型用户：28 岁，二线城市，制造业/服务业班组长或小店主，月入 7,000，有信用卡但额度用满，不愿向亲友开口。手机为中端安卓（1,500~2,500 元档，Android 11~13）。
- **设备含义（直接影响选型）**：安卓占比预估 75%+，中低端机型 → 包体必须控制、首屏必须轻、低端机不能卡。
- **心理**：对"日息万分之几"无感，对"借 8,000 元每月还 726"有感 → 定价展示必须给**月供**，不能只给利率。
- **抗性**：对通讯录授权、人脸识别高度敏感 → 必须逐项说明用途，且授权页要给"为什么需要"的解释，否则流失率会飙到 60%+。

### 2.2 B 端角色（运营后台 /admin）

| 角色 | 职责 | 关键权限 | 高频操作 |
|------|------|----------|----------|
| **运营 operator** | 产品配置、活动、内容 | 产品参数、Banner/公告、优惠券、消息模板 | 改额度区间、发券、改首页文案 |
| **信审 reviewer** | 人工复核件 | 查看申请详情、调额、通过/拒绝 | 处理 MANUAL_REVIEW 队列 |
| **风控 risk** | 策略与名单 | 规则/评分卡参数、黑白名单、决策阈值 | 调阈值、加黑名单、看拒绝原因分布 |
| **催收 collector** | 逾期案件处置 | 案件池、分案、催记、承诺还款（PTP） | 打电话、记催记、标记 PTP |
| **财务 finance** | 资金与对账 | 放款/回款流水、对账、息费分成 | 日终对账、导出流水 |
| **管理员 admin** | 账号与审计 | RBAC、操作审计、系统参数 | 加人、查日志 |

**权限模型**：RBAC（角色-权限点），P0 用固定 6 角色 + 权限点表，不做自定义角色（避免过度设计）。所有敏感操作（查看明文身份证、调额、免息、核销）**强制写审计日志**。

## 三、业务全流程与状态机

### 3.1 主流程（11 个节点）

```
[1] 注册登录        手机号 + 短信验证码 → 发放 JWT（access 2h / refresh 30d）
     ↓
[2] 实名三要素      姓名 + 身份证号 + 银行卡号/手机号 → OCR 模拟 + 三要素核验模拟
     ↓
[3] 活体检测        眨眼/摇头动作序列 → 返回活体分 + 人脸图（模拟厂商 SDK 回调）
     ↓
[4] 联系人授权      2 个紧急联系人（姓名+关系+手机号）+ 通讯录 hash（可选）
     ↓
[5] 授信申请        职业/收入/居住/借款用途 → 提交授信申请单
     ↓
[6] 风控决策        反欺诈规则 → 准入规则 → 评分卡 → 决策（拒绝/通过/人工/降额）
     ↓
[7] 额度定价        score 分档 → 额度 + 利率档 + 可借期限
     ↓
[8] 借款下单        选金额/期限 → 试算 → 展示综合年化+总息费 → 勾选合同 → 提交
     ↓
[9] 放款            二次风控（同人同设备频次）→ 生成借款单 → 模拟代付 → 到账
     ↓
[10] 账单与还款     生成 repay_plan → 到期提醒 → 主动还款/自动扣款/提前结清
     ↓
[11] 逾期与催收     DPD≥1 → 罚息计提 → 催收案件 → 分案 → 催记/PTP → 回款或核销
```

### 3.2 状态机（开发必须严格实现，禁止用布尔字段拼状态）

**授信申请 `credit_applications.status`**

```
DRAFT → SUBMITTED → RISK_CHECKING ─┬→ APPROVED（自动通过，同时生成 credit_limit）
                                   ├→ MANUAL_REVIEW → APPROVED / REJECTED
                                   ├→ REJECTED（规则拒绝，带 reject_code）
                                   └→ CANCELED（用户中途放弃，超 24h 自动）
```

**借款单 `loan_orders.status`**

```
CREATED → RISK_CHECKING ─┬→ REJECTED
                         └→ APPROVED → SIGNING → DISBURSING ─┬→ DISBURSED（→ 生成账单）
                                                              └→ DISBURSE_FAILED（可重试 1 次）
DISBURSED → REPAYING → SETTLED（全部结清）
                    └→ OVERDUE → SETTLED（逾期后结清）
任意态 → CANCELED（仅 CREATED/SIGNING 可取消）
```

**账单期次 `repay_plans.status`**

```
UNPAID（未到期）→ DUE（T-3 进入待还）→ PAID
UNPAID/DUE → OVERDUE（T+1 00:00 起）→ PAID（逾期后还款）
DUE → PARTIAL_PAID（部分还款）→ PAID
```

**催收案件 `collection_cases.status`**

```
PENDING → ASSIGNED → CONTACTING ─┬→ PTP（承诺还款）→ CLOSED_REPAID
                                 ├→ CLOSED_WRITEOFF（核销，需财务审批）
                                 └→ OUTSOURCED（委外，P2）
```

**状态机硬约束**：
1. 所有状态流转必须走 `POST /api/{domain}/:id/transition`，禁止前端直接改状态字段；
2. 每次流转写 `order_status_logs`（from, to, operator, reason, created_at），后台可追溯；
3. 账单金额字段一旦生成**不可变**（除还款冲销），任何调整走"减免单"而非 UPDATE。

### 3.3 关键业务规则（容易漏、漏了就是事故）

| # | 规则 | 说明 |
|---|------|------|
| R1 | **额度循环** | 结清一笔后，可用额度按"已还本金"实时恢复，不按整笔恢复 |
| R2 | **单笔占用** | 在贷本金总额 ≤ 授信额度；同时最多 1 笔在贷（P0），P2 放开至 3 笔 |
| R3 | **借款幂等** | 下单接口以 `idempotency_key`（客户端 UUID）去重，防重复放款 |
| R4 | **还款幂等** | 还款以 `repay_no` 唯一约束，重复回调只认一次 |
| R5 | **提前结清** | 只还剩余本金 + 当期应计利息（按日计），不收剩余期利息，不出违约金 |
| R6 | **部分还款** | 先冲罚息 → 再冲利息 → 再冲本金（P1） |
| R7 | **宽限期** | 到期日 +3 天内还款不收罚息，但**上报征信口径按合同到期日** |
| R8 | **放款失败重试** | 最多 1 次自动重试，仍失败转人工；失败期间额度冻结 30 分钟 |
| R9 | **额度有效期** | 授信通过后 30 天未借款，额度失效需重新授信（P1 改为 90 天） |
| R10 | **账务日切** | 每日 00:00 跑批：计提罚息、账单状态流转、逾期案件生成、报表落库 |

## 四、计费与还款模型（开发直接用）

### 4.1 定价结构

- **不设"服务费/管理费/账户管理费"独立条目**——全部并入"综合息费"，从源头规避"砍头息"与费用拆分式误导。
- 定价档位按 **IRR 年化**配置，**月费率由系统反解**，禁止手工配置月费率直接上生产（手工配必然算错 IRR）。
- 配置项只有两个：`irrAnnual`（年化 IRR，如 0.18）与 `term`（期数）；`monthlyFeeRate` 由求解器推导。

| 风险档 | 综合年化 IRR | 授信额度 | 可借期限 | 目标占比 |
|--------|-------------|----------|----------|----------|
| A | 7.2% | 30,000~200,000 | 6/12 期 | 15% |
| B | 10.8% | 15,000~50,000 | 3/6/12 期 | 30% |
| C | 14.4% | 5,000~20,000 | 3/6/12 期 | 35% |
| D | 18.0% | 1,000~8,000 | 3/6 期 | 15% |
| E | 24.0% | 500~3,000 | 3 期 | 5% |

**上限硬约束：IRR 综合年化 ≤ 24%**（不触碰 36%，预留监管收紧空间）。任何配置或活动导致实际 IRR 超 24%，后端计算服务应**拒绝生成合同**。

### 4.2 还款方式（已按设计稿数据反推确认）

**P0：等本等息**（本金均摊 + 每期利息固定按初始本金计）——这是行业现金贷主流，也是**设计稿的真实模型**，经反推验证：`8,000 / 12 = 666.67` 本金 + `59.73` 利息 = `726.40` 月供，×12 = 8,716.80，总息 `716.80`，与设计稿完全吻合。

```
每期应还本金 = P / n                    （P=借款本金，n=期数）
每期利息     = P × 月费率 m             （注意：按初始本金计，不按剩余本金）
每期应还     = P / n + P × m            （月供固定）
总息费       = P × m × n
```

**P1：等额本息**（利息按剩余本金计，总息更低、更"合规友好"，但月供前期偏高）。用于 A/B 档优质客户。

```
PMT = P × i × (1+i)^n / ((1+i)^n - 1)      i = 月利率
```

**P2：等额本金 / 先息后本**（先息后本仅限 A 档、期限 ≤ 6 期）。

**提前结清（等本等息下的口径，对客有利，是卖点）**：

```
结清金额 = 剩余未还本金 + 当期利息 × (当期已用天数 / 当期总天数)
退还/免除 = 剩余各期利息（全部免除，不收违约金）
```
即：结清金额永远 ≤ 正常还完的总支出，页面需实时展示"提前结清可省 ¥XXX"。

> **选型说明**：等本等息对客月供最低、最易沟通，但**实际资金成本被"每期按初始本金计息"抬高**，因此 IRR 显著高于名义年化（见 4.3 换算表）。这正是监管要求明示 IRR 的原因——**产品可以做等本等息，但绝不能只展示"月费率 0.75%"。**

### 4.3 年化利率算法（**本节为合规关键，数值已实测校验**）

监管口径（央行公告〔2021〕第 3 号）：以借款人支付的所有贷款成本与其**实际占用本金**的比例计算，并折算年化，采用 **IRR** 法。

```
求 i 使：P = Σ_{k=1..n} CF_k / (1+i)^k       （P=放款金额，CF_k=第 k 期应还）
年化 IRR = i × 12
```

**必须实现的口径与用途：**

| 口径 | 公式 | 用途 |
|------|------|------|
| **年化 IRR** | 解上式得月 IRR `i`，`年化 = i × 12` | **所有对客展示、合同、账单、监管报送的唯一口径** |
| 名义年化 | `月费率 m × 12` | ❌ **禁止对客单独展示**（严重低估实际成本） |
| 日利率 | `年化 IRR / 365` | 仅营销辅助，必须与年化并列展示 |
| 平均本金单利 | `总息费 / 平均占用本金 / 年限` | 仅内部经营分析 |

#### ⚠️ 设计稿的三个数字问题（开发必须修正）

对设计稿 `8,000 元 / 12 期 / 月供 726.40 / 总息 716.80 / 综合年化 16.6%` 做反推：

| 项目 | 设计稿 | 实算（等本等息，月费率 0.7467%） | 结论 |
|------|--------|--------------------------------|------|
| 每月本金 | 660.00 | **666.67** | ❌ 660×12 = 7,920 ≠ 8,000，差 80 元 |
| 每月利息 | 66.40 → 54.40 → 42.40 → 30.40（逐期递减） | **恒为 59.73**（等本等息不递减） | ❌ 递减序列属"等额本金"，与月供固定矛盾 |
| 总息费 | 716.80 | 716.80 | ✅ 吻合 |
| 月供 | 726.40 | 726.40 | ✅ 吻合 |
| 综合年化 | 16.6% | **16.15%**（IRR × 12） | ⚠️ 差 0.45pt，需统一 |

**修正结论：设计稿的"总息费/月供/年化"三个主数值是自洽的（等本等息），但账单页的"本金 660 / 利息逐期递减"是错的，必须改为每期本金 666.67 + 利息 59.73。**

**两套可执行方案，开发二选一（推荐 A）：**

| 方案 | 月费率 | 月供 | 总息费 | 页面展示年化 | 说明 |
|------|--------|------|--------|-------------|------|
| **A（推荐，保数值）** | 0.7467% | 726.40 | 716.80 | **16.2%**（实算 16.15%） | 保留设计稿视觉与文案，仅把 16.6% 改为 16.2%，账单利息改恒定值 |
| **B（保 16.6%）** | 0.7682% | 728.12 | 737.44 | 16.6% | 数字全改，视觉不动 |

#### IRR ↔ 月费率换算表（等本等息，已实测，供配置与测试断言使用）

| 目标年化 IRR | 3 期月费率 | 6 期月费率 | 12 期月费率 |
|-------------|-----------|-----------|------------|
| 7.2% | 0.4008% | 0.3517% | 0.3286% |
| 10.8% | 0.6018% | 0.5289% | 0.4955% |
| 14.4% | 0.8032% | 0.7070% | 0.6642% |
| 18.0% | 1.0050% | 0.8859% | 0.8347% |
| 24.0% | 1.3421% | 1.1859% | 1.1226% |

> **关键认知（写进代码注释）**：同一月费率在不同期数下 IRR 不同——`0.7467%/月` 在 3/6/12 期的 IRR 分别为 **13.39% / 15.20% / 16.15%**。因此**定价必须以"目标 IRR + 期数"为键反解月费率**，不能让用户在 3/6/12 期之间切换时共用一个月费率（否则短期标的实际年化会低于合同展示，长期标的会高于展示，构成价格欺诈）。

**验收标准**：
1. 任一借款方案，`后端计算 IRR` 与 `页面展示年化` 误差 ≤ 0.01 个百分点；
2. 前端调 `POST /api/loan/quote` 取数，**前端不得自行计算利息**；
3. 单测覆盖：3/6/12 期 × 5 档 IRR × {正常、跨年、闰年 2 月、提前结清、逾期 1 天/30 天} 共 ≥ 40 组断言。

### 4.4 罚息与违约金

- 罚息率：`逾期本金 × 0.05% / 日`，自到期日次日 00:00 起计（宽限期内不计，但宽限期仅免罚息、不免征信口径）。
- 违约金：P0 不设（简化，也降低投诉风险）。
- 罚息与利息合计不得超过 24% IRR 上限；超出部分系统自动截断。
- 逾期 90 天以上转"核销/委外"候选池，需财务审批后执行。

## 五、风控与授信决策设计（P0 必须真跑，不能随机数）

> 这是"非界面演示"的核心判别点。评审时若发现授信结果是 `Math.random()`，判定为不合格交付。

### 5.1 决策链路（串行，任一步拒绝即终止并返回原因码）

```
① 设备与反欺诈  →  ② 准入规则  →  ③ 评分卡  →  ④ 额度定价  →  ⑤ 决策合成
```

### 5.2 ① 反欺诈规则（命中即拒绝，`reject_code=AF_xxx`）

| 码 | 规则 | 阈值 |
|----|------|------|
| AF_001 | 同设备 7 天内关联账号数 | > 3 |
| AF_002 | 同身份证 30 天内关联手机号数 | > 2 |
| AF_003 | 紧急联系人命中黑名单 | ≥ 1 |
| AF_004 | 申请频次（同人 24h） | > 3 |
| AF_005 | 设备为模拟器/root/越狱 | 命中即拒 |
| AF_006 | GPS 与常用地跨省突变（< 6h 内 > 800km） | 命中转人工 |
| AF_007 | 身份证号命中法院失信/黑名单库 | 命中即拒 |

### 5.3 ② 准入规则（`reject_code=AC_xxx`）

| 码 | 规则 |
|----|------|
| AC_001 | 年龄 18~60 周岁（含边界） |
| AC_002 | **在校学生一律拒绝**（职业=学生 / 学校邮箱 / 校区地址 三命中其一） |
| AC_003 | 实名三要素核验通过且姓名身份证一致 |
| AC_004 | 活体分 ≥ 0.8 且人脸比对 ≥ 0.75 |
| AC_005 | 手机号在网时长 ≥ 6 个月 |
| AC_006 | 非禁入地区（新疆/西藏部分区域、涉诈高发地名单，由风控后台配置） |
| AC_007 | 紧急联系人 ≥ 2 且不可与本人号码相同 |

### 5.4 ③ 评分卡（0~1000 分，权重可后台配置）

| 维度 | 权重 | 特征示例 |
|------|------|----------|
| 身份稳定性 | 20% | 年龄、户籍、婚姻、学历 |
| 收入与职业 | 25% | 职业类型（公务员/国企/民企/自雇/自由职业）、月收入区间、社保公积金 |
| 居住稳定性 | 10% | 居住时长、居住类型（自有/租房/宿舍） |
| 履约历史 | 25% | 模拟征信分、历史借款笔数、历史逾期次数、当前多头借贷数 |
| 行为与设备 | 20% | 设备价格档、App 使用时长、申请填写耗时（过快=中介）、资料修改次数 |

**分档映射**：≥750 → A ｜ 680~749 → B ｜ 600~679 → C ｜ 520~599 → D ｜ 480~519 → E ｜ <480 → 拒绝（`RJ_SCORE`）

### 5.5 ④ 额度定价与⑤ 决策合成

- 额度 = `min(档位额度上限, 月收入 × 倍数)`，倍数 A/B/C/D/E = 3/2/1.5/1/0.5。
- 决策结果四选一：`REJECT` / `PASS`（自动） / `MANUAL`（转人工，命中灰名单或分数临界 ±20） / `PASS_DOWN`（降档通过）。
- **全部决策落库** `risk_decisions`：入参快照、命中规则列表、各维度分、最终分、决策、额度、利率档、耗时 ms。这既是审计要求，也是后续调策略的唯一依据。

## 六、竞品拆解与差异化

### 6.1 三强对照

| 维度 | 360 借条（奇富借条） | 美团借钱 | 度小满（有钱花） |
|------|---------------------|----------|------------------|
| **额度区间** | 500 ~ 200,000 元 | 500 ~ 200,000 元 | 500 ~ 200,000 元 |
| **期限** | 3/6/12/24 期 | 3/6/12 期 | 3/6/12/24 期 |
| **定价展示** | 主打"日息 0.027% 起"，年化 7.2%~24% | 主打"日息 0.02% 起" | 主打"日息 0.02% 起" |
| **还款方式** | 等额本息为主 | 等额本息 | 等额本息/先息后本 |
| **获客路径** | 360 浏览器/搜索/安全卫士自有流量池 + 应用商店 + 短视频信息流投放 | **美团 App 内生场景**（外卖/到店支付页入口）+ 少量外部投放 | 百度搜索流量 + 度小满金融 App + 信息流 |
| **核心留存** | 额度循环、提额任务、免息券、"借条会员"权益 | 场景绑定（借钱可用于美团消费）、月付联动、会员红包 | 分层产品（满易贷/尊享贷）、邀请返现、会员 |
| **风控底牌** | 360 安全大数据（设备/网址行为） | **真实消费与履约数据**（订单、地址、退款、评价） | 百度搜索意图 + 征信 |
| **本质** | 流量生意 | 场景生意 | 流量生意 |

### 6.2 拆出来的三条行业规律

1. **定价话术已从"日息"转向"年化"**——监管强制明示年化后，"日息万分之X"的模糊空间被压缩，**透明定价不再是差异化，而是入场券**。
2. **额度 500~20 万是标准壳**，"最高可借 20 万"是获客钩子，实际件均远低于此。真正的差异在**首借通过率**与**到账速度**。
3. **留存靠"额度感"**：提额、循环额度、免息券，本质都在强化"你随时有一笔钱可用"的心理账户。这是复借率的核心杠杆。

### 6.3 UCash 的差异化与取舍

**取（做）**
- **速度**：全流程目标 3 分钟到账（模拟层内可做到 30 秒），首屏直接给额度、借款页直接给月供，减少跳转。
- **透明**：借款确认页固定四行——借款金额 / 每期应还 / 总息费 / 综合年化（IRR），任何一屏不出现"日息"单独表述。
- **额度感**：S3/S5 用户首页常驻"额度已恢复/可再借"卡片，把复借设计成一次点击。
- **小额高频**：聚焦 500~20,000 元、3/6/12 期，不与巨头在大额长期上正面竞争。

**舍（明确不做，并记录原因）**
| 不做 | 原因 |
|------|------|
| 会员/权益商城 | 现金贷会员易被认定为"变相收费"，合规风险 > 收益（P2 再议） |
| 24 期及以上长期 | 无资金方承接能力，M3+ 风险敞口过大 |
| 场景分期（先享后付） | 无自有消费场景，接入外部场景需 BD 与联合风控，超出 MVP |
| 积分体系 | 与借贷心智无关，纯成本 |
| 社交裂变（强邀请） | 金融类分享在微信生态受限，且易触发"诱导借贷"投诉 |

**差异化一句话**：巨头卖"额度上限"，UCash 卖"**这笔钱每月还多少、总共多花多少**"——用确定性换信任。

## 七、平台形态论证（为什么是 RN + Expo）

### 7.1 决策依据：先用四步法判形态

| 判断步骤 | 结论 | 推导 |
|----------|------|------|
| ① 用户状态 | 移动端优先 | 用户在资金缺口当下（多为夜间/通勤/家中）手持手机产生需求，无桌面场景 |
| ② 使用频次 | 低频（月 1~2 次）但**强提醒依赖** | 低频本应做小程序，但"到期还款提醒"是**降损刚需**，必须具备强触达能力 |
| ③ 人群设备构成 | 安卓 75%+，中低端机型为主 | 包体与低端机性能是一等约束 |
| ④ 关键动作 | 摄像头活体、通讯录读取、设备指纹、推送 | **这四项小程序与 H5 全都做不好或做不了** |

### 7.2 为什么不是纯 H5

| 能力 | H5 | 影响 |
|------|-----|------|
| 活体检测 | 只能调摄像头做"拍照"，无动作活体 SDK，攻击成本极低 | 反欺诈直接失效 |
| 通讯录读取 | 浏览器沙箱禁止 | 紧急联系人/反欺诈网络缺失 |
| 设备指纹 | 仅 UA + Canvas，弱且易伪造 | 同设备多账号识别失效 |
| 推送触达 | 无 | 还款提醒缺失 → 逾期率上升 30%+ |
| 安全性 | 无法做证书绑定/代码保护，易被中间人劫持 | 资金类应用不可接受 |
| 微信内传播 | 金融借贷类 H5 在微信内被限制分享，域名易被拦截 | 获客链路不稳 |

**结论**：H5 只能作为**投放落地页**（展示"最高可借 20 万，点击下载"），不能承载主业务。

### 7.3 为什么不是微信小程序

| 约束 | 说明 |
|------|------|
| **类目资质** | 金融类小程序需提交小贷牌照/消费金融牌照/银行合作证明，无牌照主体**无法过审**；本项目当前无牌照，直接死路 |
| 包体积 | 主包 2MB、总包 20MB（分包），金融表单+图表+活体 SDK 极易超限 |
| 原生能力 | 活体检测需微信原生插件（需厂商支持且审核），通讯录不可读，设备信息受限 |
| 后台常驻 | 无法常驻，自动扣款/静默重试类逻辑无法实现 |
| 品牌资产 | 无桌面图标，无独立品牌入口，不利长期用户资产沉淀 |

**结论**：小程序在"无牌照 + 需强风控"双重约束下，**不是可选项**。

### 7.4 为什么是 RN 而非 Flutter / 原生 / uni-app

| 方案 | 判断 | 理由 |
|------|------|------|
| **React Native + Expo（选定）** | ✅ | 团队为 TS 全栈；`packages/shared` 可让 C 端/后台/服务端**共用**金额计算、状态机、枚举、校验规则——这是本项目最大的工程红利（利息算错是资金事故）；Expo 提供 EAS 出包、OTA、原生模块按需接入 |
| Flutter | ❌ | 需另起 Dart 技术栈，共享逻辑要重写一遍；本项目 UI 复杂度中等（表单+卡片+图表），Flutter 的性能优势用不上 |
| 原生双端 | ❌ | 两套代码，工作量翻倍；本项目为验证型产品，投入产出不成立 |
| uni-app | ❌ | 优势在多端（含小程序），而小程序已被排除；复杂表单/动画体验上限低；TS 类型支持弱 |

**RN 的风险与对冲**：
- 风险：活体检测、设备指纹需原生模块 → 对冲：P0 用模拟适配层（`KycProvider` 接口），真实接入时用 config plugin 封装厂商 SDK，业务层零改动。
- 风险：低端安卓首屏慢 → 对冲：Hermes 引擎 + 首屏骨架屏 + 图片 WebP + 路由懒加载，包体目标 < 35MB。

### 7.5 推荐端组合（唯一主推荐）

> **React Native (Expo) App（C 端，iOS + Android）+ Vite React Web 后台（B 端，/admin）+ Expo Web（本地验证与投放落地页）**

- C 端 App：承载全部借贷业务，需原生能力与强推送。
- B 端 Web：运营/信审/风控是**长时桌面操作**（看列表、批件、看报表），Web 后台是唯一正解。
- Expo Web：开发期在浏览器验证交互（`expo start --web`），同时可作为投放落地页复用。

### 7.6 打包与分发路径

| 阶段 | 方式 | 说明 |
|------|------|------|
| **本地开发验证** | `expo start`（Expo Go 扫码）/ `expo start --web` | 浏览器即可验收全部流程，无需真机 |
| **内测分发** | `eas build --profile preview` | Android 出 APK 直装链接；iOS 出 Ad Hoc 包（需注册设备 UDID，上限 100 台） |
| **灰度** | TestFlight（iOS，上限 10,000 人）+ 安卓内测渠道 | 收集崩溃与转化数据 |
| **正式上架** | `eas build --profile production` → App Store Connect / Google Play / 国内安卓商店（华为、小米、OPPO、vivo、应用宝） | 每家单独提审 |
| **热更新** | `expo-updates`（仅 JS/资源层） | 修文案、调样式、修 bug 可秒级生效；**不得通过 OTA 变更核心功能或规避审核**（App Store 3.3.2） |

**上架硬性前置（缺一不可，详见第十一章）**：软件著作权、ICP 备案（后台域名）、隐私政策公网可访问、等保 2 级备案证明、金融类目资质（牌照或资金方合作证明）、App 安全评估报告。

### 8.5 MVP 范围说明（回应"功能点超 15 个"的反模式质疑）

P0 共 28 条需求，看似超出方法论建议的 15 个功能点。**理由与取舍**：
1. 现金贷是**强监管、强账务**业务，缺一个环节即闭环断裂（如无合同签署 = 无法放款；无审计日志 = 无法过等保）。
2. 已在 P0 内主动砍掉：自动扣款、优惠券、邀请、提额、工单、埋点（全部推至 P1）。这些是"提效"而非"成立"。
3. P0 不含任何"锦上添花"：无积分、无会员、无推荐、无多语言、无深色模式。
4. 若必须再压缩，唯一可砍项是 REQ-028（Banner 配置）与 REQ-026 的部分指标，但不能砍 REQ-019/022/024/027（后台四项是运营与合规底线）。

## 十二、可行性评估

### 12.1 技术可行性：**可行（低风险）**

- 全部核心能力均有成熟方案：RN + Expo（出包/OTA）、Express（业务）、better-sqlite3（单机事务足够 POC）、JWT（认证）。
- 无自研攻关点。唯一需注意：**账务计算的正确性**（等本等息 + IRR 反解月费率 + 提前结清按日计息），必须以单测覆盖 ≥40 组边界用例（3/6/12 期 × 5 档利率 × 闰月、月末、跨年、部分还款、逾期后结清）。**IRR 求解器建议用二分法而非牛顿法**（单调性好、不会发散）。
- 风险点：SQLite 单写锁 → POC 阶段并发 < 200 可接受；转生产需换 PostgreSQL（数据访问层用 Kysely/Prisma 抽象，替换成本 1~2 人日）。

### 12.2 成本可行性：**区间估算**

| 项 | 估算 | 说明 |
|----|------|------|
| 开发工作量 | **90~120 人日** | 跨端 App + 后台（方法论参考区间 60~150 人日，本项目含风控与账务，取中上位） |
| 云服务器 | 200~500 元/月 | 2C4G 起，POC 可用 1C2G |

## 十五、结论与建议

### 15.1 值不值得做

**值得做，但要分清两件事**：
- 作为**产品与技术的完整实现**（POC / 合作洽谈 Demo）：值得，且本方案可在可控成本内交付一个"真跑得通"的系统，这在与资金方、牌照方谈判时是硬通货——**没有可演示系统，助贷合作连门都进不去**。
- 作为**立即对外放款的生意**：当前不具备条件（无牌照、无资金方、无征信、无等保）。**不建议在资质齐备前对外展业**，任何"先上线再说"的做法都会把合规风险转化为行政处罚与刑事风险。

### 15.2 MVP 范围建议（一句话）

> P0 = **一条能算对钱的闭环**：C 端 16 个能力点跑通"借—放—还—逾期"，B 端 12 个能力点保证"看得见、管得住、留得痕"。其余全部推至 P1。

### 15.3 交给下游的三项输入

1. **给产品主理人**：以第二章五阶段分群为首页与流程设计基线；以第八章需求池为 PRD 骨架（REQ 编号直接复用）；4.3 节的 IRR 口径必须在 PRD 中作为**不可协商项**写死。
2. **给全栈研发师**：以第九章分层与适配层契约为工程骨架；`packages/shared/money.ts` 为唯一金额计算源；P0 DoD 见第十章。
3. **给上线发布师**：端组合 = RN(Expo) App + Vite 后台 + Expo Web；分发路径见 7.6；**软著（6 周）与等保（4~8 周）须与开发并行启动**，金融类目资质见 12.4。

### 15.4 选型结论（唯一推荐）

> **React Native + Expo（iOS/Android C 端）+ Vite React（Web 运营后台）+ Expo Web（本地验证与落地页）**。
> 备选切换条件：若 Rex 决定"仅做验证、不打算上架"，可降配为 **Expo Web 单端 + 后台**（省 30% 工作量，但失去活体/通讯录/推送能力，风控降级）；若牌照与资金方落地且要求极致体验，再评估 iOS 原生化。
